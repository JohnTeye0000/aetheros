# Day 27 — Loading programs from the filesystem

Stage 26's programs were baked into the kernel image. Now programs are **files**: they live in the filesystem, persist on the data disk, and are loaded and run in ring 3 on demand.

## The AXE1 format

Plain text, so `write`, `cat`, `ls`, `save` and `load` all work on it unchanged:

```
AXE1                     magic - rejects random text files
# comment to end of line
b8 00 00 00 00           x86-64 machine code as hex bytes
bf 07 00 00 00
cd 80
```

`usermode::parse_axe` validates before anything runs: magic present, only hex digits, even digit count per token, non-empty, at most 16 KiB. Failures print an error and run nothing.

## Commands

- `install` — writes the six built-in programs into the filesystem as `<name>.axe` (generated by `to_axe`, which hex-dumps the machine code the assembler produced).
- `exec <file>` — read → parse → spawn a kernel thread → copy into the user pages → `iretq` to ring 3.
- `save` / `load` (Stage 25) — so programs survive reboot.

`run <name>` (built-ins) and `exec <file>` now share one path, `spawn_bytes`.

## Verified in QEMU

| Test | Result |
|---|---|
| `install`, `exec hello.axe` | greeting printed from ring 3, status 0 |
| hand-typed `write exit7.axe AXE1 b8 00 00 00 00 bf 07 00 00 00 cd 80`, `exec` | `mov eax,0 / mov edi,7 / int 0x80` — **exited with status 7** (12 bytes of machine code written at the shell prompt) |
| `save`, reboot, `ls`, `exec count.axe` | programs came back from disk and ran |
| `AXE1 zz`, plain text, missing file | rejected with a clear error, nothing runs |

## Note

Hand-typing machine code is the honest "this is what an executable *is*" moment — no assembler, no ELF, just bytes the CPU runs. A real loader would parse ELF headers, set up per-process address spaces and pass argv; those are the obvious next steps.

## Limits

One process at a time, flat binary loaded at a fixed base (position-independent code only), no relocation, no arguments, 16 KiB max.
